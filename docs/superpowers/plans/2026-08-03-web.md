# Interfaz web — Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** una web local sobre la base de datos que ya llena el pipeline, para revisar ofertas clasificadas, decidir sobre ellas y mantener perfil, preferencias y búsquedas sin tocar YAML.

**Architecture:** FastAPI sirve HTML renderizado con Jinja2; HTMX se encarga de filtros y acciones sin recargar la página. No hay API JSON ni build de frontend: la web lee y escribe las mismas tablas que el pipeline.

**Tech Stack:** FastAPI, Jinja2, HTMX (servido en local, sin CDN), SQLAlchemy, pytest + `fastapi.testclient`.

**Plan anterior:** [pipeline](2026-08-03-pipeline.md) · **Correcciones:** [correcciones](2026-08-03-correcciones.md) · **Spec:** [diseño](../specs/2026-08-03-clasificador-ofertas-design.md)

## Por qué este plan describe comportamiento y no dicta código

El plan del pipeline dictaba implementaciones literales que nunca se ejecutaron, y dejó siete defectos que sólo aparecieron al correr el sistema de verdad. El documento de correcciones, que describía comportamiento y reproducción, salió mucho mejor. Aquí se especifica **qué debe hacer cada ruta y qué test lo demuestra**; el código lo escribe y lo ejecuta quien implementa.

**Regla general:** cada tarea termina con sus tests en verde y sin romper los 223 existentes. Comprobar el código de salida real de pytest, no la última línea impresa: `pytest -q; echo $?`.

---

## Lo que este plan añade sobre el spec original

El spec se escribió antes de ejecutar nada. Cinco cosas aprendidas después deben estar en la interfaz:

1. **Los descartes por regla tienen que ser inspeccionables.** Tres defectos reales se encontraron mirándolos: ofertas de ámbito nacional descartadas por un filtro de ciudades, tarifas por hora comparadas contra un mínimo anual, y una fuente entera marcada como presencial por defecto. Si esa lista no se ve, los vetos mal puestos ocultan ofertas para siempre y en silencio.
2. **Las ofertas truncadas deben ir marcadas.** Adzuna corta a 500 caracteres y el modelo juzga sobre un fragmento. El usuario tiene derecho a saber sobre qué se decidió.
3. **El cupo de JSearch es el recurso escaso**, no el LLM. Tiene límite duro mensual y debe verse antes de agotarse.
4. **Una decisión sin motivo escrito no enseña nada.** `feedback.py` las ignora. La interfaz debe empujar a escribir el porqué, no esconderlo tras un paso opcional.
5. **Presentarse es un proceso, no un estado.** El modelo actual (`interesa`/`descartada`/`aplicada`) no distingue "lo descarté yo" de "me rechazaron ellos", ni permite saber a cuántas ofertas aplicaste este mes. Medido sobre datos reales: de 26 ofertas `aplicar_ya` sólo hay 22 empresas distintas, así que la repetición ya está ocurriendo.

## Estructura de ficheros

| Fichero | Responsabilidad |
|---|---|
| `app/web/main.py` | Instancia FastAPI, monta estáticos y rutas, arranca el scheduler |
| `app/web/deps.py` | Dependencia de sesión de base de datos y helper de plantillas |
| `app/web/routes_ofertas.py` | Listado, detalle, decisiones y reclasificar |
| `app/web/routes_config.py` | Perfil, preferencias y búsquedas guardadas |
| `app/web/routes_runs.py` | Histórico de ejecuciones, descartes por regla y cupos |
| `app/web/templates/` | `base.html` y una plantilla por vista, más parciales para HTMX |
| `app/web/static/` | `estilo.css` y `htmx.min.js` |

Las rutas no contienen lógica de dominio: llaman a `app/pipeline.py`, `app/profile.py` y `app/cli.py`. Si una vista necesita lógica que no existe, va al módulo de dominio correspondiente y se prueba allí, no en la ruta.

**HTMX se sirve en local.** Nada de CDN: es una herramienta local que debe funcionar sin red, y una dependencia externa en el HTML es un punto de fallo gratuito.

### Task 2: Listado de ofertas

**Files:** `app/web/routes_ofertas.py`, `templates/ofertas.html`, `templates/_lista.html`; test `tests/web/test_ofertas.py`

La vista principal. Sobre datos reales hay ~25 `aplicar_ya`, ~32 `revisar` y ~52 `descartar`, así que el orden y el plegado importan.

**Comportamiento:**

- Agrupa por categoría: `aplicar_ya` primero, luego `revisar`, y `descartar` **plegado por defecto** — el usuario no ha entrado a leer descartes.
- Dentro de cada grupo ordena por confianza (alta primero) y después por fecha de publicación descendente; las ofertas sin fecha van al final, no al principio.
- Cada fila muestra título, empresa, ubicación, modalidad, fuente, fecha y el razonamiento. Enlace al original que abre en pestaña nueva.
- **Una oferta con `descripcion_truncada` lleva una marca visible** que explique al pasar por encima que la fuente sólo publicó un fragmento.
- Las ofertas ya decididas no aparecen en la lista principal por defecto.
- Filtros por fuente, categoría, **estado de decisión** y búsqueda de texto sobre título y empresa. Se aplican vía HTMX sobre el parcial `_lista.html`, sin recargar. El filtro de estado debe permitir ver "sólo aplicadas", "sólo en proceso" y demás, que es lo que convierte la lista en un seguimiento de candidaturas.
- **Historial por empresa**: si hay decisiones previas con la misma empresa (comparada con `normaliza_empresa()`), la fila lo indica — *"aplicaste aquí el 12 de mayo, te rechazaron"*, *"descartaste una oferta suya"*. La oferta **se muestra igualmente**: un rechazo de hace seis meses no es para siempre, y ocultarlo sin decirlo es como se pierden oportunidades sin enterarse.
- Un contador visible de a cuántas ofertas has aplicado este mes y cuántas siguen en proceso.

**Tests requeridos:**

- El orden de los grupos es `aplicar_ya`, `revisar`, `descartar`.
- Dentro de un grupo, confianza alta aparece antes que media.
- Una oferta sin fecha no adelanta a una con fecha reciente.
- Una oferta truncada incluye la marca; una completa no.
- El filtro por fuente devuelve sólo esa fuente.
- El filtro por categoría devuelve sólo esa categoría.
- Una oferta con decisión no aparece salvo que se pida explícitamente.
- La petición HTMX devuelve el parcial, no la página entera (comprobar que no incluye la navegación).

### Task 3: Estados de decisión y memoria por empresa (dominio)

**Files:** `app/models.py`, `app/decisiones.py` (nuevo), `app/feedback.py`; tests `tests/test_decisiones.py`, `tests/test_feedback.py`

Esta tarea es de dominio, no de web, y va antes que la interfaz porque las vistas dependen de ella.

**Estados nuevos**, sustituyendo a `interesa`/`descartada`/`aplicada`:

| Estado | Significado |
|---|---|
| `guardada` | Me interesa, aún no he hecho nada |
| `aplicada` | Me he presentado |
| `en_proceso` | Hay conversación en marcha |
| `rechazado_por_ellos` | La empresa me ha descartado |
| `descartada_por_mi` | No me interesa |

`decision` gana `aplicada_en` (se fija la primera vez que llega a `aplicada`, para poder contar a cuántas aplicaste en un mes) y `actualizada_en`.

**El punto crítico, y el motivo de que esta tarea exista separada:** `feedback.py` usa las decisiones como ejemplos para el clasificador, y **`rechazado_por_ellos` NO puede contar como ejemplo negativo**. Un rechazo de la empresa no dice nada sobre lo que el candidato quiere; dice que encajaba lo bastante como para presentarse. Tratarlo como negativo enseñaría al sistema a ocultar justo las ofertas que mejor encajan, y el fallo sería invisible: simplemente dejarían de aparecer buenas ofertas.

Clasificación para el few-shot:

- **Positivos:** `guardada`, `aplicada`, `en_proceso`.
- **Negativos:** `descartada_por_mi`, y sólo ése.
- **Ignorados:** `rechazado_por_ellos`.

**Memoria por empresa:** dado un conjunto de ofertas, poder saber qué historial hay con cada empresa, comparando por `normaliza_empresa()` de `app/dedup.py` — la misma función que ya deduplica, para que "Acme S.L." y "ACME SL" cuenten como la misma. Devuelve, por empresa: estados previos, fechas y a qué oferta correspondían.

**Tests requeridos:**

- Cada estado se persiste y se lee de vuelta.
- `aplicada_en` se fija al pasar a `aplicada` y **no se mueve** si luego cambia a `en_proceso` o `rechazado_por_ellos`.
- `rechazado_por_ellos` no aparece como ejemplo negativo en `ejemplos_few_shot`, ni como positivo.
- `descartada_por_mi` sí aparece como negativo; `aplicada` y `guardada`, como positivos.
- El equilibrado entre positivos y negativos sigue funcionando con los estados nuevos.
- La memoria por empresa agrupa "Acme S.L." y "ACME SL" juntas.
- Una empresa sin historial devuelve vacío, no un error.

### Task 4: Decidir sobre una oferta

**Files:** `app/web/routes_ofertas.py`, `templates/_acciones.html`; test `tests/web/test_decisiones.py`

Aquí está el mecanismo de aprendizaje del sistema: `feedback.py` sólo usa decisiones **con motivo escrito**, y descarta las demás. La interfaz tiene que reflejarlo.

**Comportamiento:**

- Una acción por estado de la tabla de la tarea 3. Cada una crea o actualiza la fila de `decision`.
- **El motivo se pide en el mismo gesto**, no en un segundo paso escondido. Debe poder guardarse vacío, pero la interfaz tiene que dejar claro que una decisión sin motivo no enseña nada al clasificador.
- Decidir dos veces sobre la misma oferta actualiza la decisión, no crea otra: `decision.job_id` es único y un `INSERT` ciego reventaría.
- Tras decidir, HTMX reemplaza sólo esa fila.
- Al marcar `rechazado_por_ellos`, la interfaz debe dejar claro que eso **no** enseña al clasificador a evitar ofertas parecidas. Es contraintuitivo y conviene decirlo donde se decide.

**Tests requeridos:**

- Cada estado se guarda con su motivo.
- Volver a decidir sobre la misma oferta actualiza en vez de fallar por la restricción de unicidad.
- Decidir sobre una oferta inexistente responde 404 y no crea nada.
- Una decisión con motivo aparece luego en `ejemplos_few_shot`; una sin motivo, no. (Este test cierra el circuito completo: es lo que hace que el sistema aprenda.)
- Marcar `aplicada` fija `aplicada_en`.

### Task 5: Detalle de oferta y reclasificar

**Files:** `app/web/routes_ofertas.py`, `templates/oferta.html`; test `tests/web/test_detalle.py`

**Comportamiento:**

- Muestra la descripción completa, el razonamiento, los cinco ejes, skills que faltan, red flags, el modelo que la clasificó y la versión de prompt.
- Botón de reclasificar que vuelve a llamar al clasificador con el prompt y las preferencias actuales, y sustituye la clasificación anterior.
- Si el proveedor falla, la vista lo dice con el mensaje real; no puede quedarse en blanco ni tragarse el error.
- Si la descripción está truncada, se indica junto al texto, no sólo en el listado.

**Tests requeridos:**

- El detalle incluye razonamiento, ejes, modelo y versión de prompt.
- Reclasificar sustituye la clasificación y actualiza `prompt_version`.
- Un fallo del proveedor deja la clasificación anterior intacta y muestra el error. Usar `FakeProvider` con excepción; ningún test toca la red.
- Una oferta inexistente responde 404.

### Task 6: Perfil

**Files:** `app/web/routes_config.py`, `templates/perfil.html`; test `tests/web/test_perfil.py`

**Comportamiento:**

- Muestra el perfil vigente en campos legibles, no como JSON crudo.
- Permite subir un PDF. Reutiliza `sincroniza_perfil()`: el mismo PDF no vuelve a llamar al modelo, uno distinto sí y avisa si había ediciones manuales.
- Permite editar el perfil a mano. Al guardar se marca `editado_a_mano`.
- Muestra el histórico de perfiles anteriores, porque al resubir un CV las correcciones manuales no se arrastran y ahí es donde se recuperan.
- Un PDF ilegible muestra el error en la propia vista.

**Tests requeridos:**

- Subir un PDF nuevo crea perfil (con extractor falso; **ningún test llama a Gemini**).
- Subir el mismo PDF no vuelve a extraer.
- Editar y guardar marca `editado_a_mano` y conserva lo editado.
- Un fichero que no es PDF se rechaza con un mensaje claro.
- El histórico lista los perfiles anteriores.

### Task 7: Preferencias

**Files:** `app/web/routes_config.py`, `templates/preferencias.html`; test `tests/web/test_preferencias.py`

**Comportamiento:**

- Formulario con salario mínimo, modalidades, zonas, sectores y tecnologías vetadas, idiomas y el campo libre de notas.
- **Las notas necesitan una explicación visible** de qué son: se inyectan tal cual en el prompt y son lo que más afina el clasificador. Hoy están vacías y eso limita el sistema.
- **Los vetos necesitan un aviso**: se descarta sin gastar llamada al modelo y sin que el usuario lo vea. Medido: vetar `java` ocultaba 3 ofertas válidas de 197.
- Al guardar, ofrecer reevaluar el prefiltro sobre las ofertas ya descartadas por regla, porque un veto retirado debería devolverlas a la cola.

**Tests requeridos:**

- Guardar persiste y se lee de vuelta con los mismos valores.
- Un salario no numérico se rechaza sin romper.
- Reevaluar devuelve a `pendiente` las descartadas por una regla que ya no aplica.
- Reevaluar no toca las ofertas ya clasificadas.

### Task 8: Búsquedas guardadas

**Files:** `app/web/routes_config.py`, `templates/busquedas.html`; test `tests/web/test_busquedas.py`

**Comportamiento:**

- CRUD completo. **Editar debe actualizar de verdad**: `carga_semilla` es idempotente por nombre y no actualiza lo existente, defecto conocido que la web no debe heredar.
- Al elegir fuentes, mostrar el coste: JSearch gasta un crédito por búsqueda y run, y con run diario son ~30 al mes de un cupo de 180. Debe verse cuántos créditos comprometen las búsquedas activas.
- Botón "buscar ahora" que lanza un run. **Con rate limit**: el aviso legal de Remotive pide un máximo aproximado de 4 peticiones diarias, así que el botón no puede permitir pulsarlo en bucle.
- El run no puede bloquear la petición HTTP: lánzalo en segundo plano y que la vista informe del progreso.

**Tests requeridos:**

- Crear, editar y borrar funcionan; editar cambia los valores existentes.
- Desactivar una búsqueda la excluye del run.
- El cálculo de créditos comprometidos es correcto para varias búsquedas con y sin JSearch.
- Pulsar "buscar ahora" dos veces seguidas no lanza dos runs.

### Task 9: Runs, descartes por regla y cupos

**Files:** `app/web/routes_runs.py`, `templates/runs.html`; test `tests/web/test_runs.py`

La vista de diagnóstico. Es la que permite descubrir que algo va mal antes de que pasen semanas.

**Comportamiento:**

- Histórico de runs con inicio, fin, estadísticas por fuente y errores. Los errores tienen forma consistente `{tipo, referencia, error}`.
- **Lista de ofertas descartadas por regla, agrupada por motivo**, con enlace a cada oferta. Es la vista que hizo aflorar tres defectos reales.
- Desde ahí, poder devolver una oferta a la cola de clasificación cuando el descarte fue injusto.
- **Cupo de JSearch del mes en curso**: consumido, límite y restante, leídos de `source_usage`.
- Ofertas en estado terminal `error` tras agotar intentos, visibles y reintentables.

**Tests requeridos:**

- El histórico muestra los runs con sus estadísticas y errores.
- Los descartes se agrupan por motivo y el recuento cuadra.
- Devolver una oferta a la cola la deja en `pendiente` y limpia `motivo_regla`.
- El cupo mostrado coincide con `source_usage` del mes en curso.
- Un mes sin consumo muestra el límite completo, no un error.

### Task 10: Arranque conjunto y scheduler

**Files:** `app/web/main.py`, `Dockerfile`, `compose.yaml`, `README.md`; test `tests/web/test_scheduler.py`

**Comportamiento:**

- `docker compose up` levanta la web en el puerto 8000 con el scheduler del run diario dentro del mismo proceso.
- El scheduler no debe arrancar durante los tests: que dependa de un ajuste, apagado por defecto en el entorno de prueba.
- El `CMD` del Dockerfile ya apunta a `app.web.main:app`; comprobar que ahora sí levanta.
- README con las instrucciones reales de arranque y uso.

**Tests requeridos:**

- La aplicación se importa y arranca sin scheduler cuando el ajuste está apagado.
- Con el ajuste encendido, el job `run_diario` queda registrado a la hora configurada.
- Verificación manual: `docker compose up`, abrir `http://localhost:8000`, recorrer las cinco vistas y comprobar que las acciones funcionan.
